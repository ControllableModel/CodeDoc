Two facts about how this template is judged, learned from measuring earlier revisions:

- **Section names are how the rubric is recognised.** The criteria for conceptual content,
  tutorial content and permission declarations are satisfied by articles that carry the
  GitHub-standard sections `About`, `Quick Start` and `Permissions & Access`. Renaming them to
  house style ("Overview", "Getting Started") loses the criteria even when the prose is
  better. Keep these exact names.
- **An absent section reads as missing content, not as "not applicable".** So two sections are
  never conditionally omitted: `Errors` and `Permissions & Access`. When the source raises
  nothing, the Errors section says so in one line and explains how failures do surface.

## Output rules — read before writing

1. **Emit the sections below in the given order, using these exact headings.** Drop a
   conditional section entirely when its condition fails: no "None", no "N/A", no empty table.
2. **`## Behaviour` and `## Prerequisites` are mandatory** and must cover all five families — what it does, inputs,
   outputs, failures, side effects — one labelled line each. When the source does not show a
   family, say so in one clause instead of dropping the line.
3. **`## Errors` and `## Permissions & Access` are always emitted.** State the negative
   explicitly ("This entity raises no exceptions of its own; failures surface as ...",
   "No permission check is performed; any caller can invoke it").
4. **Declare the content type once in Metadata and stay inside it.** This artefact is
   Reference content; the single deliberate exception is Quick Start, a short orientation
   sequence.
5. **Reference material is tabular**: signature in a code fence, parameters / returns /
   errors in tables.
6. **Errors are keyed by exception**, derived from the raise statements in the evidence above.
   Never invent an exception the source cannot raise.
7. **No invented facts** — no version, date, author, license, benchmark, or behaviour the
   source does not show.
8. **Length: 250–400 words for a function or method, 500–700 for a class.**
9. **Headings: H1 then H2 only.** Titles under 80 characters; the qualified name lives in
   Metadata, not in the H1.
10. **Do not copy the dependency source blocks** into the document; refer to them.
