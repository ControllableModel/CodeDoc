The criteria this shape of documentation most often fails, and how to avoid them:

- **Content type consistency** — an article stays inside ONE content type. This artefact is
  **Reference** content. The one deliberate exception is Getting Started, which is a short
  opening sequence, not a tutorial.
- **Reference Content** — reference information must be structured: signature, parameter
  table, return table, error table. Prose description of a parameter list is not reference.
- **Error Reference** — errors must be documented per error, separately from troubleshooting.
- **Content order** — prerequisites before usage; reference material grouped together.
- **Further Reading and Next Steps are required**, not optional: a reference page without them
  reads as a dead end.

## Output rules — read before writing

1. **Emit the sections below in the given order.** For conditional sections, drop the whole
   section when the condition fails: no "None", no "N/A", no empty table.
2. **Declare the content type once in Metadata and stay inside it.**
3. **Reference material is tabular**: signature in a code fence, parameters/returns/errors in
   tables.
4. **Errors get their own table keyed by exception**, derived from the raise statements in
   the evidence above. Never invent an exception the source cannot raise.
5. **No invented facts** — no version, date, author, license, benchmark, or behaviour the
   source does not show. Omit rather than complete.
6. **Length: 150–300 words for a function or method, 300–500 for a class.**
7. **Headings: H1 then H2 only.** Titles stay under 80 characters; the qualified name lives
   in Metadata, not in the H1.
8. **Do not copy the dependency source blocks** into the document; refer to them.
