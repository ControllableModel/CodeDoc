The criteria that documentation of this shape fails most often, and how to avoid them:

- **Content type consistency** — an article must stay inside ONE content type. Mixing a
  tutorial, a reference entry and a troubleshooting article in one page is scored as a
  violation, not as thoroughness. This artefact is **Reference** content.
- **Error Reference** — errors must be documented so a reader can recognise them, and kept
  separate from troubleshooting. A vague "Troubleshooting" paragraph does not count; a table
  keyed by error does.
- **Reference Content** — reference information must be structured: signatures, parameter
  tables, return tables, attribute tables. Prose description of a parameter list is not
  reference content.
- **Content order** — a reader needs prerequisites before usage, and reference material
  grouped together. Order the sections the way they are listed below.

## Output rules — read before writing

1. **Emit only the sections listed below, and only when the condition holds.** Omit rather
   than writing "None", "N/A" or an empty table.
2. **Declare the content type once, in Metadata, and stay inside it.** Reference content
   describes what exists; it does not teach a task step by step.
3. **Reference material is tabular.** Signature in a code fence; parameters, returns,
   errors and attributes in tables.
4. **Errors get their own table, keyed by exception**, derived from the raise statements in
   the evidence above. Never invent an exception that the source cannot raise.
5. **No invented facts** — no version, date, author, license, benchmark, or behaviour the
   source does not show.
6. **Length budget: 120–250 words for a function or method, 250–450 for a class.**
7. **Headings: H1 then H2 only.** Titles stay under 80 characters; the qualified name lives
   in Metadata, not in the H1.
8. **Do not copy the dependency source blocks** into the document. Refer to them.
